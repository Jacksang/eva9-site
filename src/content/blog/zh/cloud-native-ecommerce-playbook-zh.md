我花了二十年构建电商系统。以下是我希望第一天就有人告诉我的事情。

## 可扩展的架构（不炒作）

我见过的最大错误：在你有用户之前过度设计。

### 第一阶段：云端虚拟机上的单体应用

对于你的前 10,000 个用户，一个结构良好的单体应用在单个云虚拟机上运行完全没问题。关键准则：

**重要的：**
- 清晰的关注点分离（即使在单体应用中）
- 为最终分片设计的数据库模式
- 幂等的支付处理
- 从一开始就做好可观测性（日志、指标、追踪）

**暂时不重要的：**
- 微服务
- Kubernetes
- 事件溯源

### 第二阶段：提取瓶颈

当你遇到扩展问题时，瓶颈几乎总是三件事之一：

1. **支付吞吐量** → 首先提取支付服务
2. **库存竞争** → 使用乐观锁提取库存服务
3. **搜索性能** → Elasticsearch 或云端搜索

**一次提取一个服务**。验证。然后再提取下一个。

## 支付处理：不可妥协的原则

我在亚洲各地构建过微信支付、支付宝、信用卡和本地钱包的支付集成。一些通用的经验教训：

1. **幂等键不是可选项。** 为每次支付尝试生成唯一键。绝不重复扣款。
2. **每日对账。** 将你的账本与支付提供商的结算文件进行比对。每一天。
3. **超时 ≠ 失败。** 如果支付网关超时，交易可能仍然成功。始终查询最终状态。
4. **货币处理非常困难。** 以最小单位存储金额（分）。明确地进行舍入。绝不使用浮点数。
5. **退款走与收款相同的路径。** 不要构建单独的退款流水线。

## 市场架构

构建市场（买家+卖家）与直接电商店铺有本质区别：

### 信任问题
在直接店铺中，你信任自己。在市场里，你谁都不信。每笔交易需要：

- **托管** — 买家付款托管，确认收货后释放给卖家
- **争议解决** — 清晰的流程、证据收集、时间线
- **卖家验证** — KYC、营业执照、银行账户验证
- **评价真实性** — 仅限已核实购买、反作弊机制

### 数据模型
```
users (id, type: buyer|seller|admin)
stores (id, seller_id, name, status)
products (id, store_id, sku, price, stock)
orders (id, buyer_id, store_id, status, total)
order_items (id, order_id, product_id, qty, price)
transaction_ledger (id, order_id, type: charge|refund|payout, amount, status)
```

注意：交易账本是独立的表。绝不从订单状态推导财务数据。你的会计会感谢你的。

## 真正有效的忠诚度计划

我为多个平台设计过忠诚度系统。真正驱动行为变化的方法：

1. **积分是负债。** 从会计角度看，未兑换的积分是债务。设置过期策略。
2. **等级比积分更能改变行为。** 人们更在意身份（金卡、铂金卡），而不是多 100 个积分。
3. **简单即王道。** 如果用户无法心算出"还要多少杯咖啡才能免费"，他们就不会参与。
4. **惊喜和愉悦。** 偶尔的意外奖励比可预测的积分累积更能创造忠诚度。

## 云成本管理

"Serverless = 更便宜"的说法是危险的。Serverless 在低负载时更高效，在持续高负载时更昂贵。要了解你的交叉点。

对于典型的电商平台：

| 流量 | 推荐方案 |
|---------|---------------|
| 0-1 万日订单 | Lambda + DynamoDB（按需） |
| 1 万-10 万日订单 | Lambda + DynamoDB（预留） |
| 10 万+ 日订单 | ECS/EKS + RDS/Aurora |

记住，**永远**设置账单告警。
